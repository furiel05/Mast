# Mast 仕様書（YouTube視聴抑制 Chrome拡張）

Nov 1, 2026 · @主計さん

## 概要と目的

ChromeでのYouTube視聴を、あらかじめ決めた「予約枠」の時間帯だけに制限するChrome拡張機能を作る。枠外は例外なしでブロックし、枠を広げる変更にはスマホの認証アプリでの承認と24時間後の反映を課して、衝動的な視聴と設定変更を防ぐ。

名前は **Mast**。誘惑に負けないよう自分を船のマストに縛らせたオデュッセウスの神話にちなみ、「未来の自分を前もって縛る」という仕組みを表す。Chrome Web Storeでは「Mast – Watch-time limits for YouTube」のように、YouTube向けであることを説明文側で補足する（YouTubeのブランドガイドラインに合わせ、名前自体にはYouTubeを含めない）。

## 対象環境

WindowsとMacのChromeを対象にする。両OSで同じ拡張機能を使えることが、ネイティブアプリではなくChrome拡張を選んだ理由。

| 対象 | 方式 | 状態 |
| --- | --- | --- |
| Chrome（Windows） | Chrome拡張 | 今回のスコープ |
| Chrome（Mac） | Chrome拡張 | 今回のスコープ |
| iPhone | 自作アプリ（Screen Time API） | 将来開発 |
| Chrome以外のブラウザ | なし | スコープ外 |

## ブロックの基本仕様

予約枠のルールを満たすときだけYouTubeを見られ、それ以外は例外なしでブロックする。仕事や調べ物での一時解除ルートは、娯楽の抜け道になるため設けない。

**予約枠のルール**

曜日ごとに、次の4種類から選んで設定できる。時間帯は1日に1つだけ指定する。

| 種類 | 内容 | 例 |
| --- | --- | --- |
| 見ない日 | その日は1日中見られない | 平日は見ない |
| 時間帯 | 見てよい時間帯を指定する | 平日20〜23時、土日9〜23時 |
| 予算 | 1日に見てよい合計時間を指定する | 平日60分、土日120分 |
| 組み合わせ | 時間帯の中で、かつ予算が残っているときだけ見られる | 平日20〜23時のうち60分まで |

**1日の区切り**

- 1日の区切りは朝4時とする。曜日の判定と予算のリセットは、すべてこの時刻を基準にする（例：火曜の深夜1時は「月曜の夜」として月曜のルールで判定する）
- 区切りを0時にしないのは、夜ふかしした深夜を「その日の夜」として扱うほうが感覚に合うため
- 時間帯は0時をまたいでよい（例：22:00〜翌2:00）。ただし区切りの4時はまたげない
- 設定画面では、0時以降の時刻を「翌2:00」のように表示する
- 区切りの時刻はv1では4時に固定し、設定項目にはしない

**視聴時間の数え方（予算ルール）**

- YouTubeで動画が再生中の時間だけを数える。通常の動画、ショート動画、ライブを含む。タブがアクティブか、Chromeにフォーカスがあるか、ミュートかは問わない
- サムネイルにカーソルを合わせたときのプレビュー再生は数えない（`ytd-video-preview` の中の動画）。プレビュー以外は数える側に倒し、YouTubeの画面が変わっても数え漏れが抜け道にならないようにする
- 他サイトに埋め込まれたYouTubeの再生も数える（埋め込みiframe内でもコンテンツスクリプトを動かす）
- 同じ端末で複数のタブを同時に再生しても、重ねては数えない。どれか1つでも再生中だった時間を数える
- 計測は再生開始・停止のイベントで時刻を記録し、その差分で計算する。バックグラウンドタブのタイマー間引きや、Service Workerの停止の影響を受けないようにするため
  - コンテンツスクリプトは、再生が始まった・止まったことをService Workerに知らせるだけにする。記録の書き込みは端末ごとにService Workerの1か所で行い、タブどうしの書き込みの競合を避ける
  - タブを閉じたときなど、停止の知らせが届かないことがある。そのため、再生中は1分ごとにそのタブがまだ再生中かを確かめる
- 予算を使い切った時点でブロックし、ブロック画面には「今日の視聴時間を使い切りました」と、次に見られる時刻を表示する

**ブロック時の動作**

- 予約枠の外では、youtube.com（埋め込みを含む）へのアクセスをブロック画面に置き換える
  - 対象：youtube.com、youtube-nocookie.com、youtu.be と、そのサブドメイン（www.、m. など）
  - 対象外：music.youtube.com（音楽を聴くためのサービスなので）、accounts.youtube.com（Googleアカウントのログイン処理が通るため。ブロックすると、GmailなどほかのGoogleのサービスにもログインできなくなる）
- 予約枠が終わった時点、または予算を使い切った時点で、開いているYouTubeタブもブロック画面に切り替える
- ブロック画面には、次に見られる時刻と「タブを閉じる」ボタンを表示する
  - 次に見られる時刻は「今日 20:00」「明日（火）20:00」「11月7日（土）9:00」のように書く。この表示だけは、4時区切りではなく時計どおりの日付で書く
  - 他サイトに埋め込まれたYouTubeの代わりに表示するときは、小さく表示し、「タブを閉じる」は出さない（埋め込み先のサイトごと閉じてしまうため）
  - ブロック画面を開いたまま見られる時間になったら、「元のページを開く」リンクを表示する

## 設定変更と承認

予約枠を広げる変更には、スマホの認証アプリが出すTOTPコードの入力を必須にし、申請から24時間後に反映する。いつ申請しても、承認コードを手に入れたその日のうちには見られないので、衝動的な変更に意味がなくなる。予約枠を狭める変更は、認証なしで即時反映する。

「翌日0時から反映」にしないのは、23時55分に申請すると5分後に反映され、誘惑の強い夜の時間帯に抜け道になるため。

**広げる・狭めるの判定**

- 現在有効な予約枠と比べて、すべての曜日で「見てよい範囲」が同じか狭くなる変更だけを「狭める」とする
- 時間帯ルールから予算ルールへの変更のように、広いか狭いかを比べられない変更は「広げる」として扱う

**設定画面**

- 拡張機能のアイコンをクリックすると開く
- インストールした直後にも開く。初めての利用者が、予約枠づくりと承認コードの設定から始められるようにするため
- 曜日は月曜始まりで並べる（保存する形は日曜始まりのまま）
- 曜日ごとに「見る」のスイッチ、時間帯、1日の上限を並べる。利用者にルールの種類を選ばせず、入れた値から種類が決まる

  | 見る | 時間帯 | 1日の上限 | ルールの種類 |
  | --- | --- | --- | --- |
  | オフ | ― | ― | 見ない日 |
  | オン | 指定する | なし | 時間帯 |
  | オン | いつでも（4:00〜翌4:00） | あり | 予算 |
  | オン | 指定する | あり | 組み合わせ |

  - 見るのスイッチをオフにしてからオンに戻すと、オフにする前の時間帯と上限に戻る。初めてオンにする曜日は20:00〜23:00、上限なしにする
- 画面では「予算」という言葉を使わず、「1日の上限」と書く（「予算」は開発者向けの呼び名）
- 時間帯は、4:00〜翌4:00を表す横長の帯の上で、両端をドラッグして選ぶ。1日のどこで見られるかが一目でわかり、曜日を並べると1週間の予定表のように見えるようにするため
  - ドラッグは15分刻み。キーボードの矢印キーでも15分ずつ動かせる
  - 帯の下の時刻をクリックすると、時刻を直接入力できる（分単位）。4:00より前の時刻は翌日として扱う（「1:00」は翌1:00）
  - 0時以降は「翌2:00」のように表示する。4:00〜翌4:00のときは「いつでも」と表示する
- 1日の上限は「なし」「30分」「1時間」「2時間」のボタンと、「その他」（分を入力する）から選ぶ。選択肢を増やすと選びにくくなるので、ボタンは少なくし、2時間を超える値はあえてボタンにしない
- 上限が時間帯の長さ以上なら、「上限なし」と同じ意味になることを表示する
- 保存する前に、変更が「狭める」か「広げる」かを表示する
- 今の状態（見られるか、今日の視聴時間と1日の上限までの残り）を表示する
- 別の端末で変更された予約枠は、開いている設定画面にもすぐ反映する。編集中の内容は消さない
- 同期にはChromeの同期設定で「拡張機能」がオンになっている必要があることを、画面に書いておく

**変更予約**

- 予約中の変更は1件だけ持てる。設定画面に、予約中の内容（変わる曜日の、変更前と変更後）と反映される日時を表示する
- 予約中の変更は、認証なしで取り消せる（取り消しは狭める方向のため）
- 予約中に新しい変更を保存すると、予約中の変更は破棄され、新しい変更で判定し直す。破棄されることは、保存する前に画面に表示する
- 反映される日時を過ぎた変更は、その時刻から有効な予約枠として扱う。その時刻に端末が動いていなくても、次に判定したときに反映済みになる
  - 反映済みの予約枠を書き込むのは、次に設定を保存・取り消すときにする。Service Workerは書き込まず、複数の端末が同時に書き込んで競合するのを避ける
- ブロック画面の「次に見られる時刻」は、予約中の変更が反映されたあとの予約枠も考えて出す

**TOTPの仕様**

- 方式：RFC 6238準拠のTOTP。SHA-1、6桁、30秒
- 標準パラメータに合わせ、Google Authenticatorなどの認証アプリと、将来の自作iPhoneアプリの両方で使えるようにする
- コード検証は拡張機能内でWeb Crypto API（HMAC-SHA1）を使って行う
- スマホと端末の時計のずれを見込み、前後1つ分（30秒）のコードも受け付ける
- TOTPとBase32はライブラリを使わずに実装する。秘密鍵を扱うコードを外部のパッケージに任せないためで、RFCのテストベクトルで正しさを確かめる
- QRコードの生成だけはライブラリを使う（自前で書くと数百行になり、誤りがあると読み取れなくなるため）。依存パッケージのない小さなものを選び、バージョンを固定する

**初回セットアップ**

1. 設定画面で始める。拡張機能が秘密鍵（20バイト）を生成し、otpauth:// 形式のQRコードと、手入力用の秘密鍵の文字列を表示する
2. 認証アプリでQRを読み取るか、秘密鍵を手入力して登録する
3. 確認のため、表示されたコードを1回入力させる。コードが合ったときに初めて秘密鍵を保存する（読み取りに失敗したまま設定が済み、二度と承認できなくなるのを防ぐ）

- セットアップが済むまでは、広げる変更もすぐに反映する。最初に自分の予約枠を作るときに、24時間待たずに済むようにするため。済んでいないことは設定画面に目立つように表示する
- 別の端末でセットアップが済んでいれば（同期された秘密鍵があれば）、その鍵を使う。同時に2台でセットアップしたときは、先に保存したほうを使い、後の端末にはやり直してもらう

**設定変更の流れ**

1. 拡張機能の設定画面で予約枠を変更する
2. 変更が予約枠を狭めるだけなら、その場で反映して終了
3. 広げる変更を含む場合、拡張機能が6桁コードの入力を求める
4. 認証アプリのコードを入力し、一致すれば変更を受け付ける
5. 変更は申請から24時間後に有効になる

**秘密鍵の扱い**

- 秘密鍵は `chrome.storage.sync` で同期し、WindowsとMacで同じ認証アプリの登録を使う
- 秘密鍵は初回セットアップ時に1度だけ表示し、以降は拡張機能から見られないようにする
- 自作アプリへの移行などで再表示が必要な場合は、設定変更と同じ扱いにする（TOTP認証＋申請から24時間後に表示）。必要になるのは自作アプリを作るときなので、v1では作らない
- 拡張機能を入れ直すと鍵もリセットされるが、これは拡張機能を外すのと同じ扱いとして許容する

## 抜け道対策

Mastは、自分で入れて自分を縛るための拡張機能として、Chrome Web Storeで一般に公開する。Chromeのポリシー（管理者権限で、拡張機能の無効化やシークレットモードを禁止する仕組み）は使わない。OSの管理者向けの設定を、一般の利用者に求めるのは重すぎるため。

そのため、次の抜け道は残る。どれも設定画面とは別の場所でわざわざ手間をかける必要があり、その手間が衝動的な視聴へのブレーキとして働く。v1ではいずれも許容する。

| 抜け道 | 内容 |
| --- | --- |
| 拡張機能を無効にする・削除する | `chrome://extensions` からいつでもできる |
| シークレットモード | 拡張機能は、利用者が「シークレット モードでの実行を許可する」をオンにしない限り、シークレットウィンドウでは動かない |
| ゲストモード・別のプロフィール | 予約枠と秘密鍵はGoogleアカウント（プロフィール）ごとに分かれるため、Mastが入っていないか、設定前の状態になる |
| デベロッパーツール | 拡張機能の保存データを読み書きできる。秘密鍵を読めば承認コードを作れる |
| Chrome以外のブラウザ | 対象外 |
| 端末の時計を進める | 予約枠の判定も、変更予約の24時間も端末の時計で数えるため |

**Chrome Web Storeでの公開**

- だれでも検索して入れられる形（一般公開）で載せる
- 拡張機能ID：`fhigbpfajaapjhbihcldbofnehjojhda`
- 開発中のビルド（パッケージ化されていない拡張機能として読み込むもの）には、あえてストア版と別のIDを使う。`chrome.storage.sync` は拡張機能IDごとに分かれるため、同じIDにすると、開発中の試行でストア版の予約枠や秘密鍵を上書きしてしまう
- 集めたデータは開発者のサーバーには送らない。すべて `chrome.storage` に保存し、端末間の受け渡しはChromeの同期だけを使う。このことをプライバシーポリシー（`docs/privacy.md`）に書き、ストアの「プライバシーへの取り組み」にも同じ内容を申告する
- ストアに載せる説明文・権限の理由などは `docs/store-listing.md` にまとめる

## 設定の同期

`chrome.storage.sync` を使い、同じGoogleアカウントでログインしたWindowsとMacの間で予約枠を同期する。サーバーは不要。

- 同期する：予約枠の設定、変更予約（申請から24時間後に反映される変更）、TOTPの秘密鍵、予算の消費状況
- 予算の消費状況は、端末ごとに別キー（`usage_日付_端末ID`）で記録し、読むときに今日の日付のキーを合算する。各端末が自分のキーにしか書かないので、上書き競合が起きない（G-Counterの考え方）。日付は4時区切りで数える
- `chrome.storage.sync` は最大512件までしか保存できないため、7日より前の `usage_` キーは削除する（今日を含めて8日分を残す）
- 端末IDは端末ごとに違う値なので、`chrome.storage.local` に保存する
- 書き込み回数の上限（1分あたり120回、1時間あたり1,800回）に収めるため、書き込みは一時停止時と、再生中の1分ごとに行う
- 同期には数秒〜数分かかるため、2台で同時に再生すると予算をわずかに超えることがある。これは許容する
- Chromeの同期設定で「拡張機能」がオフだと同期されないため、セットアップ時に確認する

## 将来の拡張

iPhoneアプリを自作し、iPhoneでのYouTube視聴の抑制と、TOTPコードの生成を担わせる。TOTPを標準仕様にしておくことで、拡張機能を変えずに認証アプリから自作アプリへ移行できる。

- ブロック：Screen Time API（ManagedSettings）のWebフィルタで、youtube.com、m.youtube.com、youtu.be をドメイン指定でブロックする。YouTubeアプリはShieldでロックする
- 予約枠：DeviceActivityのスケジュールで管理する
- 要検証：ドメイン指定のブロックは、ChromeなどではSafariより効きやすいという報告がある一方、挙動がiOSのバージョンで不安定。開発ビルドで実機確認が必要
- 承認：自作アプリで同じ秘密鍵からTOTPコードを生成する

## 開発スコープ（v1）

v1はフェーズ2まで作る。フェーズ3（振り返り機能）とフェーズ4（iPhoneアプリ、同期サーバー）は対象外。

**フェーズ1：コア機能**

- [x] 予約枠のルール（時間帯・予算・組み合わせ）とブロック：Manifest V3、declarativeNetRequest
- [x] 予算の計測（再生時間）：コンテンツスクリプト、イベントベースの時間計測
- [x] 枠終了・予算切れ時のタブ切り替え：Service Worker、chrome.alarms
- [x] ブロック画面（次に見られる時刻、タブを閉じるボタン）
- [x] TOTP承認：RFC 6238をライブラリなしで実装、Web Crypto API、Base32
- [x] 設定の同期：chrome.storage.sync

**フェーズ2：品質と運用**

- [x] TypeScript＋Viteのビルド構成（WXT）
- [x] ユニットテスト（Vitest）の基盤：予約枠の判定、日付・曜日の境界、TOTP（RFCのテストベクトル）は機能と一緒に書く
- [x] E2Eテスト（Playwright）の基盤：拡張機能を読み込んだブロック動作のテストは機能と一緒に書く
- [x] GitHub ActionsでのCI
- [ ] Chrome Web Storeでの公開：アイコン、説明文、プライバシーポリシー、インストール直後の案内

**v1までの進め方**

フェーズ1とフェーズ2の残りを、PR1本程度の大きさの6ステップに分けて、この順に作る。

| # | 作るもの | 終わったときの状態 |
| --- | --- | --- |
| 1 | 予約枠の判定ロジック（`src/core/`）：時間帯・予算・組み合わせのルールから、「今見てよいか」と「次に見られる時刻」を返す | 4時区切り、曜日の切り替わり、月末、夏時間の境界がテストで押さえられている |
| 2 | 時間帯ブロック：declarativeNetRequestでのブロック、ブロック画面、枠の終了時に開いているタブを切り替える処理 | 自分で使い始められる。予約枠はひとまずコードに直接書いた初期値を使う |
| 3 | 予算の計測：動画の再生・停止イベントによる計測、端末ごとのキーで記録して合算、古いキーの削除、予算切れでのブロック | 予算ルールが実際に効く |
| 4 | 設定画面と同期：予約枠の編集（狭める変更だけを即時反映）、`storage.sync` での同期 | WindowsとMacで同じ予約枠になる |
| 5 | TOTPでの承認：Base32とTOTPの実装、初回セットアップのQRコード、広げる変更の24時間後の反映、変更予約 | 「未来の自分を縛る」仕組みが完成する |
| 6 | 公開：Chrome Web Storeでの公開の準備（アイコン、説明文、プライバシーポリシー、インストール直後の案内）、WindowsとMacの実機での確認 | v1リリース |

- ステップ2で、まず自分で使える状態にする。毎日使いながら作ると、仕様の穴に早く気づける
- 予算の計測は、YouTubeの画面の作りに左右されるため、6つの中で一番うまくいくか読めない。手戻りを小さくするため、早めのステップ3に置く
